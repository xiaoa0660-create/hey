# 照着拍

## 产品构思与 Codex Demo 说明 · v0.1

日期：2026-10-11

**产品一句话：把喜欢的参考照片，变成朋友能执行的拍摄指引。**

**首版一句话：选定参考图中的一个构图目标，上传试拍图，得到一个调整动作，再拍一张看变化。**

本文件是开放式 AI Coding 作业的产品与设计说明。目标是交付一个完整、精致、可操作的 Demo。现有用户表达与同类产品提供需求线索；本选题尚未完成目标用户测试，文中的体验优势均需通过实际使用验证。

---

## 1. 我们为什么做它

### 1.1 一个具体的使用时刻

两位朋友来到咖啡馆。小林想留下一张照片，她有一张喜欢的参考图：人物靠右，左侧有窗户和自然光，画面里保留桌上的杯子。朋友拿到手机，听到的要求是“有氛围一点”。

第一张照片里，人居中、占满画面，窗户和杯子几乎都没有入镜。小林知道效果不对，却很难迅速解释“该改哪里”。朋友也不知道是站位、取景还是人物姿势的问题，两人开始反复拍。

「照着拍」介入的时刻，是她已经有参考意图、也主动希望获得拍摄帮助的时候。

### 1.2 核心问题

**审美意图传递给拍摄动作时，出现了沟通断层。**

| 人 | 手上已经有的东西 | 当下缺少的东西 |
| --- | --- | --- |
| 想被拍的人 | 喜欢的照片、希望留下的场景 | 能把偏好表达清楚的方式 |
| 帮忙拍的人 | 手机、愿意帮忙的时间 | 足够具体、容易执行的下一步 |

我们希望减少一次拍摄中无效的解释与重拍，让双方更快得到接近既定构图目标的照片。

### 1.3 初步证据与边界

- 一位用户在摄影社区求助，想改善自己给女朋友拍照的效果：[How to take better pictures of my girlfriend?](https://www.reddit.com/r/photography/comments/17d5hef)。
- 另一位用户描述，希望人物与地标正常入镜，却长期得不到满意的结果：[My boyfriend takes ugly photos of me](https://www.reddit.com/r/whatdoIdo/comments/1sjarpg/my_boyfriend_takes_ugly_photos_of_me/)。
- TwinCam 已提供参考照片叠加到取景器以及拍摄后对比的功能：[官方产品页](https://twincam.app/?lng=en)。
- Aim 的官方页面也介绍了参考图引导与双机取景协作：[官方产品页](https://aimcamera.info/)。

这些线索说明问题与解决方式已经有人关注，不能据此推断市场规模、付费意愿或我们的产品优势。参考图辅助拍摄已有同类产品。

**本作品要验证的具体主张：先明确用户想借鉴的构图，再把一次试拍的差异翻译成一个行动，比仅展示参考照片更容易让拍摄者完成任务。**

### 1.4 产品边界

首版定位为一款两个人共同使用的轻量拍摄辅助工具，聚焦“单人半身照”的构图。产品判断围绕用户选择的人物位置、人物比例、留白展开。

摄影的光线、镜头、表情、服装、场景也会影响结果。本版只把可观察的构图目标转成指引；结果页使用“更接近你选的构图”，避免把几何匹配称为普遍的美或摄影质量。

## 2. 用户、场景与成功结果

### 2.1 第一批用户

约 20–35 岁、经常与朋友一起出门或互相拍照的人。对他们而言，“留下一张自己满意的照片”有价值，但帮助者未必掌握摄影术语。

首批使用场景是咖啡馆半身照、街边半身照、户外带背景的半身照。选择这三类场景，是为了让人像与背景关系直观、素材容易准备，也便于实际找人测试。

### 2.2 用户任务

“当我希望朋友把我拍成某种构图时，我想把喜欢的效果变成明确的拍摄动作，让我们少一点猜测，更快拍到满意的一张。”

### 2.3 三种结果分开判断

| 结果 | 如何观察 | 能说明什么 |
| --- | --- | --- |
| 操作可执行 | 拍摄者读完后能直接尝试，不再问“什么意思” | 指引足够清楚 |
| 构图接近目标 | 用户选定的人物位置、比例或留白差异缩小 | 所选几何目标得到改善 |
| 用户更满意 | 被拍者在前后照片里选择更喜欢的一张，并说明原因 | 实际审美收益 |

几何目标改善与用户满意度分别记录。用户也可以喜欢与参考图不同的构图。

## 3. 核心产品决策

### 3.1 用户先选“我喜欢哪里”

上传参考图后，提供三个选择。单次会话先选一个主要目标，完成后可以切换目标。

| 目标 | 用户语言 | 程序比较的内容 |
| --- | --- | --- |
| 人物位置 | “我喜欢人站在画面的这个位置” | 人物框中心的位置 |
| 人物比例 | “我喜欢人和背景的这个比例” | 人物框相对画面的高度 |
| 留白 | “我喜欢这里留出的空间” | 指定一侧的空间宽度 |

默认主目标由用户确认。参考图里的背景、人物长相和服装不成为匹配对象。

“留白”选择后，让用户确认左、右或上侧，并在参考图里看到被选区域。第一版只支持这三种方向，范围足够清楚。

### 3.2 每次给一个调整动作

用户上传试拍图后，画面上出现与当前目标相关的标注，再给一条短指令。可以有一句简短解释，但主界面以行动为中心。

示例：

> 调整取景，让人物靠右一点，保留左侧窗边的空间。

画面展示当前人物框、目标中心和向右的箭头。箭头描述人在最终画面中的目标位置。

另一个示例：

> 保持当前焦距，往后退一点，让人物占画面的比例更小。

画面展示当前人物框与较小的目标比例示意。因为照片没有真实距离信息，指令使用“一点”与画面示意，不输出“后退 1.2 米”等伪精确值。

### 3.3 调整动作说明给谁执行

主指引明确标为“拍摄的人”。如果有需要被拍者配合的动作，再单独显示“被拍的人”提示。第一版默认通过调整取景完成构图任务，先让拍摄者知道下一步要做什么。

照片只能支持部分构图判断。指引优先描述取景中的目标变化，不从二维图像断言精确机位高度、焦距、身体朝向或现场灯光位置。

### 3.4 让人能够纠正识别结果

人物框支持拖动与缩放。系统判断不准确时，用户调整框后重新生成指引。这个入口直接放在画面附近，文案为“人物框不准？调整一下”。

这是 Demo 的重要交互：用户能控制分析依据，后面的比较结果也能复现。

### 3.5 首版采用拍后校对

首版流程通过上传照片或调用设备允许的拍照入口，完成一次试拍与重拍。它能测试产品核心价值，也方便另一位 Codex 实现稳定的 Demo。

实时相机取景指导、连续视频分析、姿势模仿与双机同步，作为后续扩展。前端结构为相机入口留好位置，当前交付以拍后流程为准。

## 4. 完整使用流程与页面说明

界面按一个拍摄会话组织，共五个状态。用户全程知道参考图、选定目标和下一步动作。

### 状态 A：开始一张照片

**目标：让用户立刻知道用途，并愿意开始。**

- 顶部：简洁字标“照着拍”，旁边可用一枚细线取景角标。
- 主标题：“把你想拍的，讲清楚。”
- 副标题：“选一张参考，试拍一张，得到下一步怎么拍。”
- 主按钮：“选一张参考图”。
- 次按钮：“用咖啡馆示例试试”。
- 示例入口展示三张大幅摄影缩略图：咖啡馆、街边、户外。首版先完成咖啡馆完整样例，另外两张可以等素材完成后再启用。

首屏以摄影与一个明确入口为中心。功能列表与分析参数放在后续需要的位置。

### 状态 B：告诉我们你喜欢哪里

**目标：明确本次拍摄意图。**

- 主体：一张大幅参考照片。
- 下方问题：“这张图，你最想借鉴什么？”
- 三个按钮：“人物的位置”“人和背景的比例”“这里的留白”。
- 点击任意目标，照片上出现对应标注。
- 人物位置：显示人物框与中心点。
- 人物比例：显示人物框高度与画面高度的关系。
- 留白：可点左、右或上侧，显示对应区域。
- 可编辑人物框；确认裁切比例。
- 主按钮：“照这个目标试拍”。

参考图与试拍图统一使用用户确认的裁切比例。默认沿用参考图比例，用户可以改成 3:4 或 4:5，并通过拖动裁切位置确认内容。

### 状态 C：看看这张试拍

**目标：提交第一张照片并看懂差异。**

- 移动端：试拍照片居中，参考图以小窗显示，点击可以放大。
- 桌面端：参考图与试拍图并列，保持相同可比较画幅。
- 主入口：“拍一张 / 选一张照片”。浏览器不支持拍照入口时，保留文件选择。
- 处理中显示简短状态：“正在对齐人物位置……”等，文案与实际处理内容对应。
- 识别完成后显示人物框，允许确认或修正。

只有输入准备完整并确认有效人物框后，才进入可比较状态。

### 状态 D：下一步，先做这一件事

**目标：把差异转为可执行动作。**

- 顶部小标签：“你选的目标 · 左侧留白”。
- 中央：试拍图与简洁标注。
- 最重要的一张指令卡，标签：“拍摄的人”。
- 示例指令：“调整取景，让人物靠右一点，保留左侧窗边的空间。”
- 可展开“为什么”：用一句话解释差异。
- 主按钮：“再拍一张”。
- 次入口：“人物框不准？调整一下”。
- 可选入口：“保存拍摄指引卡”，将参考图、目标与动作导出成一张图片，方便现场查看。

指引卡不堆叠多个建议，也不给美貌、身材或人格打分。所有画面标注只服务于本次构图目标。

### 状态 E：看这次调整带来了什么

**目标：让用户判断变化，并结束一次完整任务。**

- 展示“第一次试拍”和“这次拍摄”，可切换并列与滑动比较。
- 两张照片对应各自人物框，显示本次目标的变化。
- 文案示例：“左侧空间更接近你选的参考。”该文案只在对应差异确实缩小时显示。
- 用户选择：“我更喜欢这张”“我更喜欢之前那张”“还想调整”。
- “还想调整”生成下一轮单步指引。
- 主按钮：“保存这张照片”。
- 次按钮：“换一个构图目标”。

成功状态以用户选择结束。参考图匹配程度可以作为解释信息，用户最终决定哪张照片值得留下。

## 5. 视觉与交互设计

### 5.1 整体方向

**摄影杂志的留白 + 取景器的清晰反馈。**

作品要像一个精致的摄影辅助产品。照片是视觉主角，文字负责解释下一步。页面里的构图线、目标点和箭头承担具体功能。

### 5.2 基础视觉规范

| 项目 | 建议 |
| --- | --- |
| 页面底色 | 暖白 `#F5F3ED` |
| 主文字 | 墨黑 `#222521` |
| 次文字 | 深灰 `#60665E` |
| 主按钮 | 深墨绿 `#273F35`，配浅色文字 |
| 图片区域底色 | 深灰绿 `#171D19`，用于照片未铺满时的留边 |
| 构图指引 | 浅黄绿 `#D7EB9A`，配深色细描边或背景，提高在照片上的可见性 |
| 分隔线 | 灰绿 `#D8DED2` |
| 圆角 | 图片容器约 20px；功能卡约 14px；避免所有控件都变成胶囊 |
| 字体 | 使用系统中文字体保证清晰；英文与数字可用本地可用的无衬线字体 |
| 字级 | 移动端标题 28–32px，主指令 20–24px，正文 15–16px |
| 触控 | 主要控件至少 44px；移动端避免依赖悬停 |

浅色文字需要深色底或可读的对比度。黄绿色优先用于照片标注，正文使用深色。

### 5.3 页面构图

移动端是首要设计对象。建议以 390px 宽的设计画板开始，并在更窄屏幕与桌面检查。

移动端：顶部为字标和“第 2 步 / 共 3 步”之类的轻量进度；中央大幅照片；下方一个关键动作区域；主按钮位置稳定，兼顾安全区域。

桌面端：主内容容器约 1120–1280px；照片区域占主要面积；参考图与试拍图可并列；目标选择与动作区域保持紧凑。

五个状态可以使用同一个工作区切换，无需做成五张无关页面。目标与参考图在切换过程中保持连续。

### 5.4 动效有用途

- 选中目标后，构图标注约 180–240ms 出现，帮助用户理解选择。
- 调整人物框时，指引跟随框的位置变化。
- 滑动比较时，只控制两张照片的显示区域；不移动或拉伸照片制造假变化。
- 分析完成后，先显示画面差异，再显示行动指令，帮助用户把原因与动作连接起来。
- 支持减少动画的系统偏好。

### 5.5 素材要求

咖啡馆样例需要三张照片：参考图、第一次试拍、重拍结果。后两张应使用同一位人物、同一场景、接近的光线，区别集中在构图上。

第一版演示可以使用有使用权限的实拍素材，也可以使用明确标注的演示素材。若用生成图准备样例，需要检查人物与场景一致性；生成图只能作为示例输入，不能充当用户实际重拍或改善结果的证据。

首版真实上传流程始终使用用户输入的照片。界面显示上传的原图与裁切结果，构图指引叠在照片上，保存时按用户选择导出。

## 6. Demo 范围：先把什么做出来

### 6.1 第一轮：完整可操作的视觉 Demo

这一轮要有漂亮且可用的全流程。示例数据必须标明“示例体验”；真实上传后，用户也能通过手动确认人物框完成计算和指引。

| 必须完成 | 验收结果 |
| --- | --- |
| 咖啡馆样例全流程 | 从开始到前后比较可以操作完成 |
| 参考图、试拍图、重拍图上传 | 页面实际显示所选图片 |
| 目标选择 | 切换目标会改变标注和指引 |
| 裁切与人物框编辑 | 可调整，比较依据可确认 |
| 单步指引 | 根据实际框位置与选定目标计算 |
| 重拍比较 | 根据重拍图数据判断变化 |
| 指引卡导出 | 生成真实可下载的图片 |
| 照片保存 | 下载对应照片；裁切导出行为与界面一致 |
| 响应式布局 | 手机、窄屏、桌面可用 |
| 返回与重新开始 | 状态一致，用户可修正前面的选择 |

### 6.2 第二轮：接入真实视觉分析

在第一轮稳定后，增加一个可替换的视觉分析接口，识别参考图与试拍图中的人物框，再让用户确认。结构上保留手动编辑与失败回退。

推荐分工：

- 视觉模型：提供人物候选框、置信度与必要的可见特征。
- 本地规则：比较用户选定的构图目标，决定优先调整什么。
- 文案生成：可选地将规则结果转成简洁中文；文案须遵循计算出的方向。

用户的审美目标、照片的几何信息、执行动作分别保存，便于调试。低置信度时请用户确认人物框。

### 6.3 后续扩展

实时相机、姿势指导、双人取景同步、多人人像、灯光建议、参考内容库、跨设备分享会话，都需要后续单独评估。当前 Demo 的完成标志是第 6.1 节的流程可用。

## 7. 给开发者的能力与数据说明

### 7.1 前端结构

如果运行环境没有既定项目，可选择一个常规的 React + TypeScript 前端。已存在项目时遵守其框架与规范。

建议组件边界：

- `SessionWorkspace`：拍摄会话与步骤状态。
- `PhotoCanvas`：图片显示、裁切、人物框、箭头。
- `GoalPicker`：本次构图目标选择。
- `InstructionCard`：一条动作与解释。
- `ComparisonView`：并列与滑动比较。
- `ImageInput`：上传、设备支持时的拍照入口。
- `GuideExport`：导出拍摄指引卡。

这些是实现参考名称，不作为产品界面文案。

### 7.2 坐标与比较规则

在确认后的裁切画幅里，用 0–1 的归一化坐标保存人物框 `{x, y, width, height}`。坐标指向裁切图像内容，不包括界面中的留边。画面上渲染时要正确计算缩放、留边、裁切和容器变化。

`crop` 使用方向校正后原图的归一化坐标；`subject` 使用裁切结果的归一化坐标。先校正照片方向，再记录裁切和人物框，保持分析、显示和导出的坐标对应。

比较示例：

- 中心：`centerX = x + width / 2`，`centerY = y + height / 2`。
- 人物比例：首版使用人物框高度 `height`。
- 左侧留白：使用 `x`。
- 右侧留白：使用 `1 - (x + width)`。
- 上侧留白：使用 `y`。

这些量是用户指定构图的代理值。人物框可能受姿势、遮挡和识别误差影响，因此必须允许确认与修正。

“留白”在此用人物边界与画面边界之间的空间代理，不判断该区域是否真的空旷、整洁或具有美感。文案使用“左侧空间”等描述，避免把复杂背景误判为空白。

目标选择、归一化坐标、容差、动作与比较结论关联起来。例如，参考图左侧留白大于试拍图时，目标箭头指向画面里更靠右的位置。容差由 Demo 调整并保存为配置，不把未经测试的阈值宣传成行业标准。

两个输入的画幅统一后再比较；图片不得被拉伸。拖动人物框后立即重算；输入变化后清除过期结果。重拍图改变时，同样重新判断。

人物框满足 `x >= 0`、`y >= 0`、`x + width <= 1`、`y + height <= 1`。目标标注也必须留在画幅内。当前人物比例过大、无法同时达到目标留白时，优先给一个缩小人物占比的动作，再在下一轮调整位置；箭头不会要求用户把人物移出画幅。

### 7.3 参考数据结构

```ts
type CompositionGoal = 'position' | 'scale' | 'negative_space';
type SpaceSide = 'left' | 'right' | 'top';

type SubjectBox = {
  x: number; y: number; width: number; height: number;
  source: 'manual' | 'vision' | 'sample';
  confidence?: number;
  confirmed: boolean;
};

type PhotoFrame = {
  id: string;
  imageObjectUrl: string;
  originalWidth: number;
  originalHeight: number;
  crop: { x: number; y: number; width: number; height: number };
  subject?: SubjectBox;
};

type Instruction = {
  goal: CompositionGoal;
  actor: 'photographer';
  action: string;
  explanation: string;
  overlay: { kind: 'move_subject' | 'scale_subject' | 'show_space' | 'matched';
    target?: { x: number; y: number; width?: number; height?: number } };
  basedOn: 'manual_geometry' | 'vision_geometry' | 'sample_geometry';
};

type ShootingSession = {
  mode: 'sample' | 'own_photos';
  goal: CompositionGoal;
  spaceSide?: SpaceSide;
  reference?: PhotoFrame;
  firstShot?: PhotoFrame;
  retake?: PhotoFrame;
  instruction?: Instruction;
  userPreference?: 'retake' | 'first' | 'continue';
};
```

真实文件、图片内容、裁切和对应框保留一致的标识。示例框属于示例图片；用户上传自己的图片后，不沿用示例的识别框。

### 7.4 AI 接口与降级行为

接口接受图像及当前裁切信息，返回人物候选框、置信度和可处理状态。模型可替换，具体供应商与模型在实际环境确定。

- 使用服务端保存密钥，浏览器不包含私密 API 凭据。
- 请求失败时保留图片，让用户手动框选人物继续。
- 用户更换图片时，过期请求的返回值不覆盖新图片。
- 找到多人时让用户选目标人物；首版仅比较一个人。
- 人物严重遮挡、未找到人物或置信度低时，让用户确认或修正框。
- 用户选择的构图已经接近目标时，显示“这个目标已经比较接近，可以按这个构图拍”，让用户决定结束或换目标。

第一轮没有模型时：真实上传使用手动人物框与真实几何计算，文案标明“按你确认的人物框生成”。演示样例标明“示例体验”。两种模式均避免表现成真实 AI 已完成任意照片识别。

### 7.5 图像与会话管理

初版默认会话内使用图片；浏览器内处理裁切、标注和导出。使用视觉接口时，在提交入口说明本次照片会发送至分析服务。

图片文件以会话内存与对象 URL 管理，清理会话时释放资源。默认只持久化用户界面偏好，不把大图写入浏览器小容量存储。分享卡由用户主动下载，跨设备会话分享暂留扩展。

上传应处理文件格式不支持、图片过大、照片方向、读取失败等情况。手机图片应保持正常方向，必要时缩小分析版本，但原图与分析图的坐标映射保持一致。

## 8. 一个完整的演示故事

### 8.1 咖啡馆样例

演示数据：参考图人物靠右、左侧留白明显；第一次试拍人物居中；重拍人物更靠右。数值仅用于示例素材，实际上传按实际输入计算。

| 图像 | 人物框示例 `{x,y,width,height}` | 左侧留白 |
| --- | --- | --- |
| 参考图 | `{0.54,0.15,0.30,0.70}` | 0.54 |
| 第一次试拍 | `{0.30,0.15,0.30,0.70}` | 0.30 |
| 重拍 | `{0.50,0.15,0.30,0.70}` | 0.50 |

用户选“留白 · 左侧”。指令让人物在画面中靠右。比较结果显示左侧留白更接近所选目标；用户自己决定更喜欢哪张。

如实际示例照片的人物位置不符合以上坐标，必须校准框的数据或换照片，使图像与数据一致。

### 8.2 60–90 秒展示顺序

1. 展示参考图：“我想拍一张窗边照片，喜欢的是人物右侧站位带来的左侧留白。”
2. 点选留白，图上对应区域亮起。
3. 上传第一次试拍，人物居中，系统标出空间差异。
4. 出现一句操作：“调整取景，让人物靠右一点。”
5. 展示重拍结果，通过比较控件看变化。
6. 选择更喜欢的照片，完成保存。
7. 使用另一张真实上传图片，调整人物框，展示指引随数据变化。

示例演示与真实输入流程分别标明。展示时清楚说明已实现的能力、采用样例的部分和视觉接口的接入状态。

### 8.3 实际小测试

Demo 完成后，可以找几组朋友，使用相近场景拍同一种构图目标。一轮使用普通参考图说明，一轮使用产品指引，交替顺序减少先后影响。

先看三件事：拍摄者是否理解操作、完成满意照片所需的重拍次数、被拍者是否更喜欢结果。记录实际反馈，不预填提升数据。小测试用于发现可用性与价值线索，不据此宣称大规模效果。

## 9. Demo 验收清单

### 产品与设计

- [ ] 首屏十秒内可以理解用途，能够直接开始。
- [ ] 参考图的构图偏好由用户确认。
- [ ] 每次只显示一个主要行动，并指出由拍摄者执行。
- [ ] 参考、试拍、重拍贯穿同一个会话。
- [ ] 图片是主角；小屏幕的指引与按钮清晰可读。
- [ ] 构图线、箭头、选中反馈都有明确用途。
- [ ] 样例标明身份，真实上传没有预制的分析结论。

### 功能与可信度

- [ ] 同一张图作为参考与试拍时，不强行给出调整。
- [ ] 人物框向左、向右或变大后，指令正确变化。
- [ ] 人物位置、比例、留白三个目标分别计算。
- [ ] 留白方向改变后，箭头与文字保持一致。
- [ ] 裁切与窗口大小变化后，标注仍对齐图像内容。
- [ ] 换参考图、换试拍图后，旧结论不会继续显示。
- [ ] 重拍更偏离目标时，如实显示，并允许继续调整。
- [ ] 用户可以选择更喜欢第一次试拍，产品接受这个选择。
- [ ] 上传与分析失败时，有可用的手动继续路径。
- [ ] 导出的指引卡与当前会话一致，照片保存真实可用。
- [ ] 手机与桌面主流程均可操作；拍照入口有文件选择回退。

这些检查用于验证核心规则、坐标和输入状态。界面微调以视觉检查为主。

## 11. 作品的表达主线

产品展示围绕三个决策展开：

1. **从主动的拍摄意图切入。**用户已经希望获得帮助，有参考图和明确任务。
2. **把审美目标交给用户。**用户选人物位置、比例或留白，系统围绕这个目标处理。
3. **把一次差异变成一次行动。**用户试拍、执行一条指引、重拍、判断结果，形成完整体验。

展示中将需求线索、待验证假设、已实现能力和实际用户反馈分别讲清楚。作品的说服力来自具体任务、设计决策和可观察的使用结果。
